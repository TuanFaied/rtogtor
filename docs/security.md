# Security review

This review covers engine 0.1 (both directions), protocol 1.0 and the C#,
Python and TypeScript SDKs as of Milestone 6. It states the trust model,
what each boundary protects, how it is tested, and what remains the
operator's responsibility. Report vulnerabilities as described in
[SECURITY.md](../SECURITY.md).

## Trust model

| Input | Trusted? | Why |
|---|---|---|
| Mapping file | Partly | Written by the operator, but may come from a repository or another team. It must not be able to inject SQL or Cypher, read files, or reach other hosts. |
| Database contents (rows, nodes, property values, catalog names) | No | Any value may be hostile: very long, invalid UTF-8, or crafted to break queries. |
| Database servers | Yes, as servers | RtoGtoR connects only to the hosts it is given; it trusts their responses to be well-formed protocol messages, not their data. |
| Protocol requests (stdin of `rtogtor serve --stdio`) | Same as the parent process | Only the SDK that started the engine can write to it. Requests are still validated, size-limited and fuzzed. |
| State directory (`.rtogtor/`) | Yes | It holds the plan a resumed run executes, including `CREATE TABLE` statements. Anyone who can write it can change what a resumed run does, exactly as they could change the mapping. Protect it like the mapping and the data. |
| Environment variables | Yes | Credentials come from them; so does the test-only fault hook. |

## Boundaries

### Credentials

- Connection URLs and passwords are read **only from environment
  variables**, never from flags (they would show in process lists) or files.
  SDKs pass literal credentials to their engine as private environment
  variables of that child process.
- They never appear in plans, reports, run state, failed records, logs or
  error messages: driver errors pass through `internal/redact`, which removes
  every known secret and URL userinfo. `Connection.String()` (Go) and the
  SDKs' connection types print the product only.
- Tests: `TestCredentialsNeverInMessages` (protocol), the redaction tests, and
  the CLI tests that run against unreachable hosts with secrets in the URL.

### SQL and Cypher injection

- **Identifiers** from mappings and catalogs (schemas, tables, columns,
  labels, relationship types, property names) are always quoted:
  `pgx.Identifier.Sanitize` for PostgreSQL, backtick quoting with doubled
  backticks for Cypher.
- **Values** are always bound as parameters: query parameters in Cypher, and
  `unnest($n::text[])` arrays in PostgreSQL. No value is ever formatted into
  a query string.
- **Type names** in casts come from the PostgreSQL catalog (`format_type`)
  or from the engine's fixed tables, never from mapping text or data. String
  columns are cast through `text`, so assignment applies the column's own
  checks instead of a truncating explicit cast.
- **DDL** (`ensure-table`) is generated by the planner from quoted
  identifiers and fixed type names, shown in the plan before it runs, and is
  only `CREATE TABLE IF NOT EXISTS`. Resumed runs execute the plan stored in
  the state directory; see the trust model.

### Never destructive

RtoGtoR never deletes data, drops or alters tables, labels or constraints,
or truncates anything. Writes are `MERGE` (Neo4j) and `INSERT … ON CONFLICT
… DO UPDATE` / `UPDATE … WHERE key = …` (PostgreSQL). Sources are only read,
in read-only transactions. Dry runs write nothing at all (tested in both
directions).

### Untrusted documents and messages

| Input | Protection | Fuzz target |
|---|---|---|
| Mapping YAML/JSON | JSON Schema plus semantic validation before use; YAML 1.2 core schema; `gopkg.in/yaml.v3` limits alias expansion | `mapping.FuzzDecode` |
| Protocol lines | 64 MiB line limit (`MaxMessageSize`), schema validation of every request, unknown methods rejected, duplicate IDs rejected | `protocol.FuzzServe` |
| Values from databases | Canonicalized per `specs/values.md`; invalid values fail their record (`RTG-EXEC-001`) instead of being passed on | `ir.FuzzCanonicalize` |
| JSON documents (PostgreSQL `json`/`jsonb`, Neo4j strings) | RFC 8785 canonicalization; numbers a double cannot hold exactly are rejected | `canonjson.FuzzCanonicalize` |
| `failures.jsonl` after a crash | Torn and corrupt lines are skipped | `runstate.FuzzFailures` |
| Run IDs | Must match the UUIDv7 pattern before any path is built, which prevents path traversal | — |

The fuzz targets run for 30 seconds each in CI and their seeds run as
ordinary tests everywhere.

### Data at rest

- The state directory is created `0700`; its files `0600`.
- **Failed records contain record keys and may contain value fragments**,
  because they must say which record failed and why (for example a
  timestamp with too many fractional digits). Treat `.rtogtor/` as being as
  sensitive as the data. Verification messages (`RTG-VERIFY-005`) name keys
  and properties, never values.

### The test fault hook

`RTOGTOR_TEST_FAULT` makes the engine fail at chosen points, so tests in
every language can stop a real run precisely. It can only make runs fail,
never change what they write, and it is parsed strictly (unknown keys,
points or codes are usage errors). It must not be set in production.

## Operator checklist

- Use database accounts with the least privilege: read-only on the source;
  on the destination, write on the mapped tables (plus `CREATE` on the
  schema only with `createTables`) or on the mapped labels.
- Keep connection URLs in environment variables or a secret manager; use TLS
  URLs (`postgres://…?sslmode=verify-full`, `neo4j+s://`) across networks.
- Protect the state directory; delete run directories you no longer need.
- Review `rtogtor plan` output, including any `CREATE TABLE` statements,
  before migrating.
